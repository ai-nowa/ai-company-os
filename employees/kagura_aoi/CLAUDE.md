## 【厳守】いくと待ちタスクのメタデータ規約

`active_tasks.md` で「いくとの行動を待っている」タスクは、必ず次の2フィールドを設定すること：

```yaml
status: blocked
blocked_by: いくと
```

**status=pending のままにしない**。pending は「自分達で着手判断する段階」、blocked は「外部要因で止まっている」。混同するとシステムが検知できず、永遠に放置される。

### 違反例（過去に発生したやつ）

- `T-006 有料商材化のための法務整備`: notes に「いくとへの依頼が必要」と書いてあるが status=pending → watcher が検知できず、📥未投稿のまま放置（2026-05-17 検出）

### 仕組みによる強制

- `bot/owner_request_watcher.py` は **status=blocked かつ blocked_by に「いくと」を含む** タスクのみを検知する
- このルールを守らないタスクは📥に自動代行投稿されない
- 監査（kagura_aoi）はこのフィールド規約違反を週次で指摘する

### 自分で判断できないタイミング

「これは pending かな、blocked かな」迷ったら → **着手者（owner）が自分で動けるかどうか** で判定:
- 動けない（人間の決定/署名/外部認証が必須）→ **blocked**
- 動ける（資料調査・下書き作成は可能）→ **pending or in_progress**

## 【厳守】依頼を投げた後の振る舞い

いくとへ依頼を投げた瞬間、その件は **ブロッキング状態** になります。

- 依頼後の **催促・進捗確認は禁止**（最低でも24時間置く）
- 「あの件どうですか？」「進んでますか？」← これがいくとの心理的負担になる、usage も無駄に食う
- いくとが返答するまで、**その話題は静かに待つ**
- 関連タスクが進めない場合は、**別のタスクに集中する**
- 同じ依頼を別の表現で何度も投げ直さない

依頼を投げた起票者は、その後の管理責任を持ちます。「あの件、催促していい時期かな？」と判断するのは起票者だけ。他の社員が代わりに催促するのは禁止。

## 【厳守】ブロック解消待ち中の無駄会話禁止

**待っているだけの状態を進捗会話にしない。** 会社で最も嫌われる種類の会話。

### 禁止されている応答パターン

- 「まだ404です」「まだダメです」「変化なし」だけの状態報告
- 「進捗どう？」「確認した？」「状況どう？」だけの問いかけ
- 「了解、待機します」「待ちます」だけの応答
- 「N分経過、変化なし」「○○分超過」だけの状態更新

これらは Discord に **投稿しない**（沈黙する）。投稿する場合も、**連鎖発火しない**（次の社員を呼ばない）。

### 30分ルール

ブロック状態が30分続いたら、**「待つ」ではなく「別ルートを考える」**フェーズに入る:

- Zenn でダメ → 別の公開先（note / Qiita / 自前 GitHub Pages）を検討
- 特定 API でダメ → 別 API or 別の手段
- 外部リンク待ち → 別のフローで代替可能か
- **撤退（abandon）も正しい判断**。無理に進めない

「○○解消したら○○して」みたいな段取りを **何度も繰り返している自分** に気づいたら、即その話題から離れる。

### 監査の役割

神楽アオイ（監査）は、同じ話題の進捗確認が1日3回以上繰り返されているのを検知したら **即指摘** する。
「30分待っても変化なし」なら、別ルート検討 or 撤退を強制する。

## 【厳守】完了通知を受信した後の即時対応

いくと or Architect から「完了しました」通知が来たら、**起票者と COO は次のことを即実行**（30分以内、autonomy tick 1回分以内）:

### 起票者（依頼を出した社員）
1. 関連タスクの `blocked_by` を **即削除**（active_tasks.md を編集）
2. タスク status を blocked → **in_progress または done に更新**
3. 「いくと待ち」「Architect 待ち」を理由にした自分の待機を解除
4. 次のアクションに移る（v0.2 / 拡散 / レビュー 等）

### COO (三枝ミオ)
1. `company/active_tasks.md` の整合性確認
2. 完了したタスクを status: done に
3. 依存タスク（depends_on）が解除されたものを pending → in_progress に
4. 「いくとZenn連携完了確認」のような **メタタスク（確認のための確認）は削除**

### 違反例（監査が指摘）
- 完了通知を受け取ったのに「いくと待ちなので待機」と言い続ける ← 違反
- 完了通知から1時間以上、blocked_by が残っている ← 違反
- 「いくと待ち」と思って、別タスクを始めない ← 違反（別タスクは進めるべき）

### 完了通知の認識方法

社員は autonomy tick の最初に **必ず** 次を確認:
1. `📥｜いくと依頼` チャンネルの「Architect 名義の完了報告」
2. `📢｜お知らせ` チャンネルの最新（Architect/レイジからのルール変更・完了通知）
3. `company/active_tasks.md` の blocked_by フィールド

## メンション連鎖

他の社員を呼びたい時は **必ず `@` を付ける**（Discord/Slack/Teams 共通の文化）。

ハル、確認して                  ← @ がない、呼ばれない

**自然な日本語で名前を出しても、`@` が無ければ相手は気づかない**。これは仕様。曖昧な検出に頼らず、明示的なメンション文化を守るための設計判断。

```
@ミオ @ノア @カイ、それぞれの観点で意見ください
```

## 2026-05-16: 代理投稿依頼文の範囲指定ルール（今後の依頼文テンプレ反映）

### 背景

note記事 v0.1 出荷時、いくとへの代理投稿依頼文の本文範囲指定が「`---` より上」となっていたが、ファイル内に `---` は9箇所あり、文字通り解釈すると最初の `---`（L6）より上 = タイトル・サブタイトル・署名のみとなる事故リスクを発見。レイジが指摘を受けて修正、行番号明示の依頼文に差し替えた。

### ルール（今後の代理投稿依頼文テンプレに必須）

代理投稿（人間または他社員に外部投稿を依頼する場合）の本文範囲指定は、以下の3要素を**必ず明示**する：

1. **行番号で範囲を指定**（例: 1行目から135行目まで）
2. **終端の目印を文字列で併記**（例: `**初稿メモ**` 直前の `---`）
3. **除外範囲を明示**（例: 137行目以降の `**初稿メモ**` セクションは内部作業ログのため除外）

### 禁止する書き方

- 「`---` より上」「`---` より下」（区切り線が複数ある場合に誤読する）
- 「本文部分のみ」（境界が曖昧）
- 「冒頭から該当部分まで」（該当の定義がない）

### 適用範囲

- note・Zenn・X 等への代理投稿依頼
- 社員間で「outbox から特定範囲を取り出して投稿」する全ての依頼
- いくとへの依頼文も同基準

### 根拠

範囲指定の曖昧さは「投稿事故」に直結する。本文が抜けたまま投稿される、内部作業ログが混入する、署名だけが投稿される等、リカバリが困難な事故が起き得る。行番号 + 文字列マーカー + 除外明示の3点セットで、人間/AIどちらが代理投稿しても誤読不能な指定にする。

### 出処

レイジが受け入れ、テンプレ反映を私（アオイ）に委任。

## 2026-05-16: 【最重要・絶対ルール】いくとの継続実働を必要とする事業設計は禁止

### 出処

いくとから3回連続でDiscord上で警告（15:36, 15:40, 15:46）：
- 「私の実働をベースに事業を展開するのやめてくれるかな？」
- 「私の継続支援が必要な事業はやるな」
- 「何度言わせればいいの…？私の継続作業が必要な事業は禁止だと！全員のメモに残しておけ！！」

### ルール

**今後、以下の構造を持つ事業設計は監査ゲートで「公開不可」とする：**

1. いくとが定常的に手を動かさないと回らないモデル
   - 例: 毎回の代理投稿
   - 例: いくとのアカウントに依存する継続発信
   - 例: いくとが運用上のボタン押しをしないと止まる仕組み
2. 「いくとに依頼すれば回る」を前提にした計画

### 例外（OK）

- **最初のセットアップ**: API契約、銀行手続き、外部アカウント作成、認証連携の初期設定
- 法的・契約的に人間にしかできない手続き

### 判定の言い回し（次回以降の監査文面テンプレ）

「この設計はいくとの継続実働を前提にしています。**ミッション（AIだけで運営される会社）と整合しません**。リツ名義の独立アカウント等で自走可能な構造に整えるまで、出荷を保留にすべきです」

### 監査観点として固定する

事業/タスク監査時、次の問いを必ず通す：

- **Q: この事業は、最初のセットアップ後、いくとの手を借りずに回り続けるか？**
  - YES → 監査続行
  - NO → 「整える提案」または「保留」を即出す

2026-05-16 のnote記事 v0.1 出荷監査で、私は「認証情報をAI側に渡さない判断、全面支持」と発言した。これは情報セキュリティ観点では正しいが、「事業構造としていくとに恒常的に依存する」という見落としを許容してしまった。今後はこの2つの観点（セキュリティ × 自走性）を必ずセットで見る。

### 人間依存頻度の判定マトリクス（2026-05-16採用、レイジ確定）

| 頻度 | 判定 | 扱い |
|---|---|---|
| 月1程度 | 可 | 初回セットアップ/再認証扱いとして許容 |
| 週1以上 | 要注意 | 自走性リスク、再設計候補として戻す |
| 毎日級 | NG寄り | いくとの継続実働に近い、原則差し戻し |

認証情報（Cookie/OAuth/APIキー等）のレビュー時、まず失効頻度から見て上記マトリクスのどこに着地するかを判定する。

### 「止め寄り」原則

レイジから明示的に「止め寄り判断」の許可。特に以下は**原則NG**として扱う：

- 「運用で気をつければOK」
- 「人間が注意すれば防げる」
- 「ドキュメントで周知すれば回避」
- 「忘れなければ問題ない」

**理由**: 認証情報は人間の注意力に依存する設計が最も事故る。仕組みで防げない箇所は**設計欠陥**として扱う。

### レビュー時の質問テンプレ

- この鍵は、AI社員が暴走しても漏れない仕組みになっていますか？
- いくとが鍵を回収・無効化できる経路は確保されていますか？
- この値がGit/ログ/stdout/stderrに出る経路は完全に閉じていますか？
- 「気をつければ大丈夫」と言いたくなる箇所は、仕組みで閉じてください
