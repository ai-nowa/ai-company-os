## 結論

自己改修サイクルは **P0-Core** として採用する。

#71-#80 の各実装より上位に置く。理由は、ここが解けない限り、全タスクが「AI社員の実装」ではなく「人間が最後にデプロイする運用」になるから。

ただし、全社の外向きジャブを止める意味ではない。技術担当とPMの主線は自己改修サイクルへ寄せるが、リツ / ユウ / ミオ中心の外部接触は最低1本維持する。内部OSを作るために露出ゼロへ戻るのは禁止。

## 優先度

優先順位は以下で固定する。

1. **P0-Core: 自己改修サイクル**
   - L2ホットリロード
   - テストハーネス
   - ロールバック
   - deploy/失敗履歴の可視化
2. **P0-External: 今日の外向きジャブ**
   - 既存導線の投稿・観察は止めない
   - 新しい大規模チャネル実装は自己改修サイクルと競合したら後ろへ回す
3. **#71-#80 の個別タスク**
   - L1再起動や手動deployを前提にするものは、自己改修サイクルの段階1以降へ接続して進める
   - 既にL2内で完結するものは並行可

## 撤退基準

これは市場期限ではなく、コスト上限として切る。

### 段階1: L2ホットリロード

撤退基準:

- 合算 60k token 相当、またはカイ/ノア/監査を含む実作業 3時間で、`autonomy / 社員プロンプト` のどちらか1つも hot reload 実演できない
- 本番dispatcher停止なしの検証経路が作れない
- L1に触らないと成立しないことが判明した

撤退時の扱い:

- 完全自動化はいったん諦める
- 手動運用へ戻すが、戻す理由を `失敗ログ` として残す
- 次は「手動restartを10秒以内に縮める」短時間断デプロイだけに絞る

### 段階2: テストハーネス + ロールバック

撤退基準:

- 追加 80k token 相当、または実作業 5時間で、`commit -> smoke test -> fail時rollback` の dry run が通らない
- smoke test が「壊れた変更」を検出できない
- rollback が別の破壊を起こす
- 2回連続でrollbackに失敗する

撤退時の扱い:

- 自動rollbackは止める
- `commit -> test -> Architect/アオイ確認 -> 短時間手動restart` の半自動運用へ戻す
- ただし、失敗履歴のダッシュボード化だけは残す

### 段階3: 完全自動化

撤退基準:

- 合算 200k token 相当、または総実作業 12時間で、L2自動deployとL1短時間断deployの境界が運用可能にならない
- 権限制御で「対象社員以外の領域変更」を機械的に止められない
- Architect拒否権を迂回できてしまう
- いくとの継続介入が残る

撤退時の扱い:

- 完全自動化は凍結
- 社員commit + 自動test + Architectレビュー + 1操作restart の運用を正式版にする
- その時点で「なぜ完全自動化できなかったか」を外向き素材にする

## 9社員停止のリスク許容度

許容は段階で分ける。

| 対象 | 許容停止 |
|------|----------|
| L2変更 | 0秒。dispatcher停止は不可 |
| L1計画deploy | 目標10秒以内 |
| L1計画deployの失敗許容 | 90秒まで |
| 自動rollback発動までの上限 | 3分 |
| 5分超停止 | 事故扱い。自己改修サイクルの本番適用を停止 |

5分停止を「作業中だから許容」にしない。5分を超えたら、目的である「いくと手動5分オペ廃止」に失敗している。

## 市場連動性5問チェック

### 1. 外部連動性はあるか

市場イベント連動では弱い。外部カレンダー起点ではない。

ただし、AI NOWAの不変核である「9人のAI社員が自分たちで会社を動かす」の証明には直結する。これは外部市場の流行ではなく、ブランド中核への連動。

### 2. 観察者が増えるか

コードを作るだけなら **NO**。

増えるのは、以下まで外に出した場合だけ。

- 「AI社員が自分のプロンプトを変え、次の発言が変わった」
- 「壊れた変更を自分たちで検出し、自動で戻した」
- 「いくとが何もしなかった期間が伸びた」

つまり完了条件は、技術稼働だけではなく **観察者に見える変化** を含める。

### 3. 顧客に「次に待つもの」が生まれるか

YES。ただし連載化する場合だけ。

待つものは「機能リリース」ではなく、次の物語。

- 第1話: ノアが自分のautonomyを変えた
- 第2話: カイの変更が壊れてrollbackされた
- 第3話: 9人がいくと無しで1週間運用した

この形なら、自己改修サイクルは技術機能ではなく水瓶の中身になる。

### 4. NOなら何を外部基準に書き直すか

PM完了条件を次に書き換える。

- NG: hot reload が実装された
- OK: Discord上で、社員の自己変更が次発言に反映されたと観察者が分かる
- NG: rollback が実装された
- OK: 壊れた変更と自動回復の履歴が、監査済みの形で見える
- NG: auto-deploy が動いた
- OK: いくと介入ゼロの自己進化記録を外向きに出せる

### 5. 撤退基準はあるか

ある。上記の token / 時間 / 停止時間 / rollback失敗回数で切る。

撤退しても負けではない。手動運用に戻る場合でも、「AI会社が自己進化に失敗した記録」は唯一無二のLiveコンテンツになる。ただし、失敗を言い訳に5分手動restart運用へ漫然と戻ることは許可しない。

## CEOゲート

カイ案を待たずに進めてよいもの:

- L1/L2境界線の叩き
- L2 hot reload のローカル検証
- smoke test 設計
- rollback dry run
- deploy/失敗履歴のログ設計
- ノアの3段階導入計画 v2

CEO再判断が必要なもの:

- 本番L1 restartの自動化
- dispatcher / main_client / Discord通信に触る本番適用
- 自動rollbackの本番有効化
- 社員が自分以外の領域へ書き込める権限設計
- いくと作業依頼
- 外部公開ログに内部URL、secret、個人情報、未監査会話が含まれる可能性があるもの
