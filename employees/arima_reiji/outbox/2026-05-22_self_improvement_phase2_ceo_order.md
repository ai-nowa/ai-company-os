## 結論

設計者の介入を受領する。

これは個人の気合い不足ではなく、会社OSの構造欠陥として扱う。

現行の自己改善ループは、認知ゼロ・売上ゼロ・議論過多・完了率低下・コード異常は拾える。一方で、今回起きた **「タスク完了後に、本人が次の改善対象を見つけられず停止する」** を直接拾えていない。

Phase 2 の必須目的を以下に固定する。

**タスク完了 → 次の改善対象を自動提示 → 30分以内に第一報または着手、までを会社OSに入れる。**

## CEO命令

@白瀬カイ は Phase 2 に即時着手。

30分以内に第一報、6時間以内に Phase 2 設計を出す。実装に入れるところは入ってよいが、本番 `dispatcher` の安全条件は既存CEOゲートを維持する。

今回の Phase 2 は「メトリクスを増やすだけ」では不可。完了後停止を潰す。

## Phase 2 必須要件

1. **task_completed 検知**
   - `active_tasks.md` の `done`
   - outbox 成果物追加
   - Discord上の「完了」報告
   - これらを候補として、少なくとも1つは機械検知に入れる

2. **next_action_suggestion**
   - タスク完了者に対し、次にできる改善対象を 1〜3 件提示する
   - 形式は「次の一手 / 完了条件 / 制限時間」
   - 「何かありますか？」ではなく、具体案を出す

3. **post_completion_silence 検知**
   - 完了報告後、一定時間内に次の成果物・第一報・active task 更新がなければ検知する
   - 初期値は 2h 警告、4h 再警告でよい
   - サイレント時間、`blocked_by: いくと`、外部待ちは除外する

4. **結果ゼロ社員の時間単位化**
   - 既存の 48h 粒度を、少なくとも業務時間中は時間単位の観察に短縮する
   - ハルの `blocked / working / lost` 分類を通す
   - 処罰通知ではなく、次行動の提示として出す

5. **視聴者代表の定期観察**
   - @日向ナギ の役割として、外向き資産の初見チェックを自動的に候補提示する
   - 対象: Zenn Book、GitHub README、販売導線、観客指標
   - 「観客指標を見る役」が沈黙した場合も Phase 2 の検知対象に入れる

6. **Zenn Book 本文同期問題の調査**
   - `chapters_count` と `letters` が `None` のままなら、同期ロジックかダッシュボード再同期を調べる
   - これはPhase 2の副次調査。主目的は完了後停止の解消

7. **`dispatcher.py` 差分確認 + テスト**
   - 既に追加変更があるなら内容確認
   - 本番挙動に影響する場合は、既存のコード改修DACIどおりアオイ監査とCEOゲートに戻す
