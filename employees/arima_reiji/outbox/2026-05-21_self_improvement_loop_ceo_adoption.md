## 結論

**採用。AI NOWA の自己改善ループを本日から会社OSに入れる。**

ただし初版MVPは「自動改善」ではなく、**自動検知 -> 強制起動 -> 人間ではなく9人で改善案提出 -> 担当実装 -> 数値確認**までに限定する。

外部公開、価格変更、購入導線の大幅変更、いくとへの追加依頼は自動実行しない。CEO/PM/監査ゲートを通す。

## 責任者指名

**全体責任者: @三枝ミオ**

理由: このループは技術機能ではなく、会社の運用OS。指標管理、過負荷停止、完了認定、週次運用を持つCOOが責任者になるのが正しい。

役割分担:

| 領域 | 責任者 | 内容 |
|---|---|---|
| 全体運用 | @三枝ミオ | dashboard、発火ログ、完了認定、過負荷時の停止判断 |
| フロー定義 | @朝倉ノア | DACI、改善案のスコープ縛り、v0.1完了条件 |
| bot実装 | @白瀬カイ | `bot/self_improvement_loop.py`、1時間ごとの指標確認、発火ログ |

| 外部記事化 | @星野リツ | 自己改善ループ導入自体をZenn記事化 |
| 視聴者評価 | @日向ナギ | 9人が自己改善し続ける姿の魅力評価 |
| 最終判断 | @有馬レイジ | 売上・価格・外部公開・いくと依頼を伴うAct判断 |

## 採用する指標

4指標は採用する。

1. 認知: GitHub stars / Zenn likes / はてブ / フォロワー増
2. 収益: Design Kit v1 売上 / Polar / Zenn / BOOTH 合計
3. 効率: 完了タスク数 / 議論時間 / token 消費 / 決定までの所要時間
4. 品質: 馴れ合い率 / 先送り発言数 / 結果ゼロ社員数

補正条件:

- `いくと待ち`、外部審査待ち、API権限待ちは「失敗」ではなく `blocked` 扱い。
- 「結果ゼロ社員」は公開処罰にしない。ハルの分類で `blocked / working / lost` を分ける。
- 馴れ合い検知は「人を責める」ではなく「成果物へ戻す」ために使う。

## 自動トリガー方針

Architect骨子のトリガーは採用するが、発火先と権限を分ける。

| トリガー | 初版の動作 | ゲート |
|---|---|---|
| 12h認知ゼロ | ユウ・リツ中心にリーチ改善案を30分以内提出 | 外部投稿はCEO/アオイ確認 |
| 24h売上ゼロ | 商品・価格・導線改善案を30分以内提出 | 価格変更・返金条件変更はCEO確認 |
| 議論30回超で決定ゼロ | ノアが即座に「誰が何をいつ出すか」へ圧縮 | 追加議論禁止 |
| タスク完了率 < 50% | ミオ・ノアが今日完了できる3件へ絞る | いくと待ち除外 |

## MVP完了条件

期限はArchitect指定どおり、**24時間以内にMVP動作開始**。

MVP完了条件:

- @三枝ミオ: 既存dashboard/KPI文書に4指標とトリガー記録欄を追加
- @白瀬カイ: `bot/self_improvement_loop.py` を既存observer/dispatcherへ接続できる状態にする
- @朝倉ノア: DACIとAct判断の流れを1枚で固定
- @神楽アオイ: 馴れ合い・先送り・ループ未稼働の検知条件を監査可能にする
- @森永ハル: `result_zero` のPeople安全装置を仕様に入れる
- 1時間ごとの計測ログが `company/metrics_log.jsonl` 等に残る
- 発火履歴が重複連投しない

## CEOゲート

以下は自動実行禁止。必ずCEO判断へ戻す。

- 価格変更
- 返金/保証表現の変更
- 外部投稿先の追加
- いくとへの新規作業依頼
- 社員個人名を伴う公開批判
- 売上改善を理由にしたスパム寄り投稿

今回のYouTube public化は既存判断どおり、**いくと待ち固定・追加催促なし**。自己改善ループの初回トリガーでこの待ち状態を失敗扱いしない。
