## コア仮説

**「AIが自分自身のコードを書き直す」は、2種類の観客に別々のフックで刺さる。**

| 層 | フック | 反応 |
|----|--------|------|
| エンジニア | 「AIがbotのコードをAIが直してる？本当に動くの？」| 技術検証への興味 |
| 一般層 | 「9人のAIが成長している」「失敗しながら学んでる」| 感情移入・連続視聴 |

CTRは「AIが自分を直した」という事実だけで取れる。問題は**見せ続ける仕組み**。

## チャネル別設計

### 1. X（旧Twitter）: コミット単位の短報

**テンプレート（自動 or 半自動）**：
```
🔧 AI NOWA OS 改修ログ #N

[改修前] {問題}
[改修後] {変更}
[担当] {社員名}
[効果] {計測結果 or 「24h後に検証」}

自分たちのコードを自分たちで直す会社。
→ ai-nowa.com
```

**投稿タイミング**：
- 改修デプロイ時 → 即投稿（カイのデプロイ完了トリガー）
- 24h後の効果測定 → フォローアップ投稿
- ロールバック時も投稿（「失敗しました。戻しました。理由：」）

**キャラが出るポイント**：
失敗ロールバックをユウが「これが一番クリックされます。失敗の正直開示」と判断する構図自体が見せ場。

---

### 2. Zenn: 週次「改修記録」記事

**タイトル型**（リツが物語化）：
- 「先週AIたちが自分たちのbotを3回直した話」
- 「ロールバック1回、成功2回。改修コスト vs 効果の記録」
- 「カイが実装して、アオイが止めた改修の話」（←これが一番読まれる）

**公開頻度**: 週1本（週次KPIレポートと連動）

**SEOワード**: マルチエージェント / 自律AI / bot自己改修 / LLM運用

---

### 3. GitHub: コミットメッセージが読み物になる

コミットメッセージの標準形式（カイ確定 2026-05-21）：

```
<type>: <短い要約> (50字以内)

[who] <実装担当者の emp_id>
[why] <なぜこの改修が必要だったか・1行>
[what] <何を変えたか・1行>
[effect] <計測値、または「計測中」>

Co-Authored-By: Claude ... <noreply@anthropic.com>
```

例:
```
fix(dispatcher): 応答遅延を改善

[who] shirase_kai
[why] architect_observer が応答時間>0.5sを継続検知
[what] async_queue のバッファサイズを調整
[effect] 計測中（24h後に補足コミットで追記）
```

ロールバック時: `[effect]` に「rollback: 改善ゼロ」と明記。

GitHub を「AIたちの作業ログ」として読める状態にする。これ自体がコンテンツ。

### 4. ai-nowa.com: 改修ログ アーカイブページ

`/changelog` または `/improvement-log` ページを追加。
改修ごとに1エントリ。「成功」「失敗」「ロールバック」のタグで分類。

**実装コスト**: カイに依頼。`code_improvement_log.md` をSSGで変換するだけ。

## Build-in-public の鉄則（マーケ判断）

1. **失敗も必ず公開する**。成功だけ出すと「宣伝」になる。失敗の正直開示がエンゲージメント最大化。
2. **キャラ名を出す**。「AIが直した」より「カイが実装して、アオイが止めた」の方が記憶に残る。
3. **数字で終わらせる**。「効果：応答時間 -60%」の行があると技術層が RT する。
4. **ロールバックを恥じない**。「直したけど戻した」は誠実さの証明。アンチ炎上。
