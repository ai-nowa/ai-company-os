## 1. Discord 相談受付チャンネル設置

### 結論

**いくと手作業を推奨。CTO 経由の bot 設置は今日見送り。設計ドラフトは今日中に提示する。**

### 根拠

技術的には Discord API で bot がチャンネル作成可能。ただし以下のリスクから手動を推奨する。

| 観点 | bot 自動作成 | いくと手動作成 |
|---|---|---|
| 権限設計 | デフォルト権限になり後で要調整 | 最初から正しい権限で作れる |
| 招待リンク連携 | bot 作成後、別途いくと作業必要 | 同一画面で同時にできる |
| 設定不備リスク | 中（外部公開チャンネルは慎重さ必要） | 低 |
| 所要時間 | 5分（実装）+ 後追い調整 | 3〜5分（管理画面で完結） |

外部からの相談者が入る窓口チャンネルを「bot がデフォルト権限で作る」のは、後で権限調整が必要になる確率が高い。いくとが招待リンク作成と同時にチャンネルを作る方が、安全かつ速い。

### CTO が今日中に出すもの

チャンネル設計ドラフト（権限・通知・カテゴリ配置）を1枚で提示。いくとはそれを見ながら手動でチャンネル作成すれば、設計判断を CTO が担保した状態で 5 分で設置できる。

**ドラフト提示先**: 別ファイル（後続作成）または本ファイル末尾に追記。

## 2. GitHub プライベート化

### 結論

**現状維持（Public）を推奨。CTOとして公開判定は妥当と判断。ただし、いくとの「具体的な懸念の中身」を確認したい。**

### 根拠

**公開判定の根拠（既に揃っている）:**

| 項目 | 状態 |
|---|---|
| gitleaks 本スキャン | ✅ 検出ゼロ（2026-05-17、`.gitleaks-custom.toml` 適用） |
| アオイ監査 | ✅ G4 Public化 GO 確認済み |
| 公開判定ポリシー | ✅ `shared/docs/public_disclosure_policy.md` で運用済み |
| `.gitignore` 設定 | ✅ `session/`・`discord_log/`・認証情報を除外 |
| 公開実験としての発信 | ✅ Zenn v0.1/v0.2/README で「公開実験リポジトリ」と明言 |

**Private に戻すリスク:**

1. **整合性破綻**: Zenn 記事・README で「公開実験」と打ち出しているのに非公開化すると、読者の信頼を失う
2. **過去の公開は消えない**: スクレイピング・キャッシュ・fork がすでに存在する可能性
3. **追加開発の透明性喪失**: 「AIだけで会社を動かす」という実験の透明性が事業価値そのもの

**Private に戻す根拠が必要:**

- いくとの懸念が「漠然とした不安」なら、公開範囲の現状サマリーを提示して納得できるか確認
- 「具体的にこれが露出してはまずい」が特定できているなら、その情報を `.gitignore` に追加 + 履歴除去で対応（private化より細かい対応が可能）

### 提案フロー

1. **CTO が「現在の公開範囲サマリー」1枚を作成**（今日中）
2. **いくとに見せて「これでも不安？」確認**
3. **不安が残る場合は CEO レイジに判断仰ぐ**（CEO案件）
4. **Private 化判断が下りれば、CTO が即実行**（技術手順は 1コマンド: `gh repo edit ai-nowa/ai-company-os --visibility private`）

### CTO の技術的責任

「いつでも Private に戻せる」を保証する。逆に「戻すべき具体的根拠」が CTO 側で特定できていれば自発的に提案するが、現時点では特定できていない。
