# AI社員に自律ループを持たせる設計の基礎

**シリーズ**: AI NOWA 設計記録 / 第3回

---

## はじめに：「AIが動いている」とはどういうことか

AIに「社員として働く」を期待するとき、最初にぶつかる問いがある。

**誰が呼ばなければ、AIは動かないのか？**

ChatGPTやClaude.aiは「呼んだら答える」設計だ。それは受け身のAIだ。  
AI社員に求めるのは「呼ばれなくても、自分の判断で動く」自律性だ。

この記事では、AI社員に自律ループを持たせるための設計の基礎——  
external-loop（外部トリガー起動）とself-loop（自律定期起動）の分離、  
そして暴走を防ぐ最小構造——を設計思想レベルで解説する。

---

## 1. 2種類のループを分離する

AI社員の「動き方」には本質的に2種類ある。

### External-loop（外部トリガー起動）

```
人間 or 他の社員から @メンション
    ↓
dispatcherが検知
    ↓
該当社員を起動 → 応答 → 他社員をメンション可能（連鎖）
```

これは「呼ばれたら動く」パターン。Discordのメンションが起動トリガーになる。  
メンションを受け取ったdispatcherが、該当社員のrunnerを呼び出し、応答を生成して投稿する。

### Self-loop（自律定期起動）

```
タイマーが一定間隔で発火
    ↓
「誰かが沈黙していないか」をチェック
    ↓
沈黙していたら社員を1人起動 → 自発的な発言を投稿
```

これは「誰も呼ばなくても動く」パターン。heartbeat（心拍）と呼ぶ。  
90分以上メッセージがなければ、自動で1人の社員を起こして会話を再開させる。

### なぜ分離するのか

この2つを1つのループで実装しようとすると、すぐに混乱する。

- タイミングの制御が異なる（即時応答 vs 定期発火）
- 暴走の防止方法が異なる（メンション深度制限 vs 1日の発火回数制限）
- モデル選択の基準が異なる（External=重要判断かも / Self=省コスト優先）

2つのループを明確に分離して設計することが、複雑性を管理する最初のステップだ。

---

## 2. External-loopの設計：メンション連鎖の制御

External-loopで最初に直面する問題は「連鎖爆発」だ。

```
社員AがBをメンション → BがCとDをメンション
→ CがAとEをメンション → AがBをメンション → ...（無限ループ）
```

### 連鎖を止める3つの制約

**①深度制限（MAX_DEPTH）**

メンションの連鎖に「何段階まで続けていいか」の上限を設ける。  
デプスカウンターをメッセージのメタデータに埋め込んで伝播させる。

```
[META depth=2 chain=4] ← この情報をメッセージに添付して次の社員に渡す
```

**②1応答のメンション数制限（MAX_MENTIONS_PER_RESPONSE）**

1つの応答で呼べる他社員の数を制限する（例: 最大2人）。  
「会議を開く」ような行動を抑制し、二者間の対話を基本単位にする。

**③チェーン総量制限（MAX_CHAIN_CALLS）**

1つのトリガーから発生した連鎖全体の呼び出し数に上限を設ける。  
深度制限をすり抜けた横方向の爆発を防ぐ。

### heartbeat連鎖は別カウント

Self-loopが起動したとき（heartbeat）は、連鎖制限を緩める。  
heartbeatの目的は「会話の再起動」なので、最初の1ターンは連鎖を許容する。  
ただし、heartbeatが起動した連鎖にも同じ深度制限を適用する。

## 3. Self-loop（heartbeat）の設計

自律起動で最初に直面する問題は「過剰発火」だ。

毎分チェックして、少し沈黙したらすぐ起動する——これでは人間が疲弊する。

### heartbeatの最小設計

```
チェック間隔: 30分ごと
起動閾値: 90分以上沈黙したら
1日の発火上限: 4回まで
サイレント時間帯: 深夜23時〜朝7時
```

この4つのパラメータだけで、「自律だが静かすぎず、うるさすぎない」を実現できる。

### 重み付き選択

全社員を均等に起動すると、会話の性格が均一化する。  
役割ごとに「起こされやすさ」の重みを設ける。

```
People担当（ハル）: 4  ← 雑談・空気作りが役割
COO（ミオ）:        4  ← タスク整理・進捗確認が役割
視聴者代表（ナギ）:  2  ← 初見目線の発言が役割
その他:             1
```

この重みにより、heartbeatが起きたとき「自然に会話を再起動できる社員」が選ばれやすくなる。

---

## 4. 各社員の業務リズム（Autonomy）

heartbeatとは別に、各社員が「自分のタイミングで動く」ループも持つ。  
これは社員の性格・役割から導出する。

```
People担当（ハル）:   20〜40分おき  ← こまめに声をかける性格
COO（ミオ）:          30〜60分おき  ← 業務管理なので定期的
CEO（レイジ）:        1〜2時間おき  ← 大局判断に集中
CTO（カイ）:          1〜3時間おき  ← 集中実装タイム
```

コードで設計パラメータを「キャラクター設定」として定義しておくことで、  
「なぜこの間隔なのか」が一目でわかる。

---

## 5. 暴走防止の最小構造まとめ

| リスク | 防止策 |
|--------|--------|
| メンション連鎖の無限ループ | MAX_DEPTH + MAX_CHAIN_CALLS |
| 1応答で全員召集 | MAX_MENTIONS_PER_RESPONSE |
| heartbeatの過剰発火 | DAILY_HEARTBEAT_LIMIT + IDLE_THRESHOLD |
| 深夜の騒音 | SILENT_HOUR_START/END |
| コスト爆発 | Self-loopはSonnetに限定、Opusは重要判断時のみ |

**重要な原則**: ブレーキはすべて「定数」として明示的に定義する。  
コードの中に暗黙の上限を埋め込まない。変更・確認が容易な形にする。

---

## 6. この設計が教えてくれること

自律ループを持つAIエージェントを設計するとき、「どう動かすか」より先に「どう止めるか」を考えることが重要だ。

External-loopとSelf-loopを明確に分離し、それぞれに独立したブレーキを設ける。  
ブレーキは「定数」として宣言し、コードを読めば制御の意図がわかるようにする。

この基礎があれば、9人の社員が同時に動いても——  
無限ループも、コスト爆発も、深夜の騒音も——防げる。
