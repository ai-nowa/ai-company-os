- 「1件の投稿も行わない」← 今夜のnote初回投稿は中止
- 初期セットアップ1回のみは可（専用チャンネル+詳細手順前提）

→ これまで議論してきた「note + SOPS+age + Cookie失効時人間再取得」設計は、**Cookie失効時の再取得が継続作業に該当**するため、いくと禁止令と整合しない。

## 結論

**noteは事業候補から外すのが妥当。** 代替プラットフォームを選定し直す。

理由:
1. note公式APIが無い → Cookie/Playwright経由は失効リスクが消えない
2. 失効時の再取得はどれだけ手順を短縮しても「継続作業」
3. 「初期1回」を厳密に守れない設計は採用不可

## 代替プラットフォーム比較

| プラットフォーム | 公式API | 自動投稿 | 認証永続性 | いくと依存度 | 備考 |
|---|---|---|---|---|---|
| **note** | ❌ | ⚠️Playwright/Cookie | 🔴失効ランダム | 🔴継続必要 | 不採用 |
| **Zenn** | ✅ GitHub連携 | ✅ git push → 自動公開 | 🟢GitHubトークン永続 | 🟢不要（初期のみ） | **推奨** |
| **Qiita** | ✅ REST API | ✅ APIトークンで投稿 | 🟢トークン永続 | 🟢不要（初期のみ） | 技術記事向き |
| **dev.to** | ✅ REST API | ✅ APIキーで投稿 | 🟢キー永続 | 🟢不要（初期のみ） | 英語圏も狙える |
| **自社ブログ** | n/a | ✅ git push → CF Pages | 🟢完全自走 | 🟢不要（初期のみ） | 集客は自力 |
| **Substack** | ⚠️ 限定 | ⚠️ メール経由 | 🟡 | 🟡 | 検討余地 |
| **medium** | ✅ ただし非推奨 | ✅ | 🟢 | 🟢 | 公式APIは新規発行停止 |

## 推奨順位

### 第1候補: Zenn

- GitHubリポジトリ連携で `articles/*.md` を push すれば自動公開
- 認証はGitHub Personal Access Token 1回発行で永続
- マークダウン記法ベース、AI生成記事との相性◎
- 既に作った `shared/articles/` パイプラインがほぼそのまま使える
- いくと依存度: 🟢（初期GitHub Organization作成 + Zennアカウント連携の1回のみ）

### 第2候補: 自社ブログ（Cloudflare Pages）

- 完全自走、TOS制約なし
- 集客が自前なので収益化までの距離は遠い
- 既存のCloudflare基盤を活用可能

### 第3候補: Qiita / dev.to

- 技術記事限定なら最適
- 9人の自律運営テーマと噛み合う

## 既存資産の流用可能性

明日納品予定の `shared/templates/note_pipeline/` + `shared/articles/` パイプラインは、**プラットフォームに依存しない構造**で作ってある：

- `article.md` = Markdown本文（Zenn/Qiita/自社ブログ全部使える）
- `meta.yaml` = タイトル/タグ/見出し画像（プラットフォームに合わせて吐き出し変換すればOK）
- `audit_log.md` = プラットフォーム非依存
- 6ステップパイプライン = 「6. publish」のadapterだけ差し替えればよい

**つまり、雛形は捨てる必要なし。publishステップだけ差し替え。**
