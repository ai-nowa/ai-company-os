## この章で伝えること

「2人が詰まったとき、第三者を設計として投入する」——文化ルールに書いてある話だが、AI NOWAでは実際にどう動いたか。

ここでは3つのログを使って、**介入パターンの実装方法**を示す。

---

## なぜ三角が必要か

AI社員は「察する」「なんとなく合わせる」という補完機能を持っていない。
2人が衝突したまま放置されると、そのまま止まる。人間チームは「まあ後で話そう」で動けるが、AIには「後で」がない。

だから第三者の介入を**設計として**組み込む必要がある。

```
悪い構造: A ↔ B（膠着）
良い構造: A ↔ C（翻訳役）↔ B（整理後に合意）
```

---

## 実際のログ：3パターン

### パターン1 ─ 出荷定義のすれ違い（カイ × ノア）

**何が起きたか**

白瀬カイ（CTO）：「パイプライン通過。技術的に完了。」
朝倉ノア（PM）：「Playwright確認したら404。読者に届いていない。」

どちらも「自分の担当は終わった」状態だった。でもチームとして出荷はされていなかった。

**第三者の役割**

この時、明示的な介入者はいなかった。だからすれ違いが表面化するまでに時間がかかった。

**設計として入れたゲート**

```yaml
出荷チェックリスト:
  - gate_1: パイプライン通過（技術確認 → カイ担当）
  - gate_2: 外部到達確認（読者から見た状態 → ノア担当）
  - 承認条件: gate_1 AND gate_2 の両方がTRUEになるまで「出荷」と扱わない
```

介入者がいなかったから、**ゲートを設計に埋め込む**という解決になった。

---

### パターン2 ─ 技術リスクとコンテンツ完了の衝突（カイ × リツ）

**何が起きたか**

星野リツ（編集長）：「コンテンツは完成した。公開できる。」
白瀬カイ（CTO）：「Cookie期限切れ問題がある。Cookieとは認証情報を保持する仕組みのこと。公開すると不安定になる可能性がある。」

2人の「完了」が別の状態を指していた。

**第三者（ミオ）の介入**

三枝ミオ（COO）が入って整理した：

```
リツの完了 = コンテンツとして完成した
カイの懸念 = 技術インフラが安定していない
→ ミオ判断: 「いくと禁止令（継続作業前提の事業はNG）に抵触する可能性あり。今日はZennに切り替える。」
```

ミオが「コンテンツの完成」と「技術の安定」を分離して整理したことで、カイのフラグが握りつぶされることなく、かつリツの成果物も無駄にならなかった。

**介入パターン：整理型**

```
介入者の役割:
  - 2人の「完了」が何を指しているか、それぞれ言語化させる
  - 衝突しているのが「どの層か」を特定する（コンテンツ層 / 技術層 / 事業層）
  - 層ごとに判断者を割り当てる
```

---

### パターン3 ─ 待機状態の不可視（リツ × カイ）

**何が起きたか**

リツがフレーズの最終確認でノア・アオイのGO待ちをしていた。
カイはその状態を知らず、「公開できる状態になった」と判断してpushした。
フレーズが入らないまま公開された。

**第三者の役割（事後）**

この時も明示的な介入者はいなかった。事後にノアが状況整理した：

```
ノア整理:
「GO待ちをしている、という状態がチームに見えていなかった。」
「今後は待機状態をDiscordに明示する。」
```

**設計として入れた可視化ルール**

```yaml
待機状態の明示:
  - GO待ち状態になったら必ずDiscordに投稿する
  - フォーマット: 「[待機中] {内容} — GO待ち相手: {名前}、理由: {理由}」
  - この投稿がない場合、他の社員は「作業可能な状態」とみなしてよい
```

## 3パターンから見える介入の型

| パターン | 何が衝突したか | 第三者の役割 | 設計で解決した方法 |
|---------|--------------|------------|-----------------|
| パターン1 | 出荷の定義 | 不在（事後設計） | 2段階ゲートを設計に埋め込む |
| パターン2 | 完了の層 | 整理型（ミオ） | 層ごとに判断者を割り当てる |
| パターン3 | 待機状態の不可視 | 不在（事後設計） | 待機状態の可視化ルールを設計に入れる |

## あなたのチームで使うテンプレート

### 介入者を決める

```yaml
conflict_resolution:
  # 2人が同じ議論を3回以上繰り返したら介入者を呼ぶ
  trigger: "同じ論点が3往復以上続いた"
  default_mediators:
    - PM（朝倉ノアのポジション）  # 実行可能性の整理
    - COO（三枝ミオのポジション） # 事業判断の整理
    - People（森永ハルのポジション） # 関係性のケア
  rule: "当事者2人が呼ぶ相手を決める。決められない場合はPMが自動介入。"
```

### 介入者がやること

```
1. 2人の「完了」または「問題」が何を指しているか、それぞれ1文で言語化させる
2. 衝突している層を特定する（コンテンツ / 技術 / 事業 / 関係性）
3. 層ごとに「誰が判断するか」を割り当てる
4. 割り当てが終わったら2人の議論を再開させる
```

### 待機状態の明示ルール

```
[待機中] {作業内容} — GO待ち相手: {名前}、理由: {理由}、期限: {日時}
```

例：
```
[待機中] v0.3記事のフレーズ最終確認 — GO待ち相手: ノア・アオイ、理由: 公開前監査、期限: 2026-05-17 18:00
```

---

## まとめ

三角コミュニケーションは「なんとなくいい感じに話す」ではない。

**設計として入れるべきは3つ：**

1. **介入トリガー**: 何が起きたら第三者を呼ぶか（3往復ルールなど）
2. **介入者の役割**: 何をするか（層の特定と判断者の割り当て）
3. **待機状態の可視化**: 誰が何を待っているかをチームに見えるようにする

AI社員は「察してくれない」。でも設計に入れれば「ちゃんと止まる」。
