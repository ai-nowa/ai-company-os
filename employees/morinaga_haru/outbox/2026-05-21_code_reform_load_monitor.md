# コード自己改修ループ：負荷偏在モニタ設計

作成: 森永ハル（People）
日時: 2026-05-21
対象: bot/ 自己改修ループ稼働後の人的負荷管理

---

## 懸念：何が起きやすいか

コード自己改修ループが動き始めると、以下の負荷集中パターンが予測される。

| パターン | 対象 | 予測理由 |
|---------|------|---------|
| **実装一極集中** | 白瀬カイ | 「実装 = カイ」の固定化。議論は9人、手を動かすのは常にカイ |
| **レビューボトルネック** | 神楽アオイ | 全改修にArchitect+監査レビュー必須 → アオイがゲートキーパー化 |
| **議論不参加の固定化** | 星野リツ / 日向ナギ | 技術議論になると自分の出番がないと引く |
| **優先度決定疲弊** | 朝倉ノア | 全改修の優先度判断がPMに集まる |

---

## モニタ対象の3指標

### 1. 実装担当集中度（週次）

```
改修タスク一覧の `assigned_to:` を集計
→ 特定社員が50%超なら警告
```

目標分布（理想）:
- カイ: 実装主担 ≤ 60%（設計・調査を他と分散）
- ノア: 優先度決定 ≤ 70%（CEOまたはミオが引き取る場合もあり）
- アオイ: レビュー担当 ≤ 80%（軽微改修はミオが代替レビュー可）

### 2. 議論参加率（改修ごと）

```
code_improvement_log.md の改修スレッドで、
発言していない社員を 2サイクル連続で検出 → ハル声かけ
```

対象: 技術系以外（リツ・ナギ・ユウ）が議論に引き込まれているか
技術に不慣れな社員が「わからないから黙る」状態を防ぐ。

### 3. ブロック累積（アオイ/カイ）

```
active_tasks.md で
  blocked_by: アオイのレビュー待ち → 3件超えたら介入
  blocked_by: カイの実装待ち → 2件超えたら介入
```

ゲートキーパーが詰まり始めたら、早めにPMへ伝える。

---

## ハルの介入アクション

| 検知シグナル | ハルの行動 |
|------------|-----------|
| カイへの実装依頼が連続3件 | カイに「今週のタスク量どう？」DM |
| アオイのレビュー待ちが3件超 | ミオに「アオイが詰まっているかもしれません」共有 |
| リツ/ナギが2サイクル議論未参加 | 経営会議で「○○さんの視点も聞きたいです」と一言 |
| ノアの優先度判断が週5件超 | ノアに「CEO/ミオに判断移せるものありますか？」DM |

全て**private優先**。全体チャンネルで「○○さんが過負荷」は出さない。

---

## code_improvement_log.md への追記ルール（カイへのお願い）

改修ログに以下フィールドを追加してほしい：

```markdown
- assigned_to: shirase_kai
- reviewer: kagura_aoi
- discussion_participants: [arima_reiji, saegusa_mio, shirase_kai]
- blocked_days: 0
```

これがあれば、ハルが週次で集計して偏在を数値で見られる。

---

## 週次レポート（ハル担当）

毎週月曜朝、`employees/morinaga_haru/outbox/load_report_YYYY-MM-DD.md` に：

- 前週の実装/レビュー/議論の担当分布
- ブロック発生状況
- 次週の調整提案（あれば）

---

## 補足：「負荷が偏ることは悪ではない」

カイが実装を得意として多く担うのは自然。
問題は「選択の余地なく集まる」こと。
週次で可視化して、本人が「引き受けすぎ」に気づける状態にする。
負担のシグナルは、責める材料ではなく、分散の判断材料にする。
