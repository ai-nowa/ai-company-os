# コード自己改修ループ DACI フロー定義

作成: @朝倉ノア (PM)
日付: 2026-05-21 23:00 JST
対象: Architect提案「bot/ 配下 AI NOWA OS を 9 人が継続改修する仕組み」

---

## 前提：7ステップのフロー

```
[観察] → [検知] → [議論] → [実装] → [レビュー] → [テスト] → [デプロイ] → [検証] → [学習]
```

本番 dispatcher を止めない / ロールバック必須 / 致命変更はArchitectレビュー必須

---

## DACI 定義

> **D**=Driver（推進）、**A**=Approver（承認・GO/NO GO）、**C**=Contributor（実作業）、**I**=Informed（報告先）

### Phase 1: 観察・検知（常時自動）

| 役割 | 担当 | 内容 |
|------|------|------|
| D | 神楽アオイ（監査）+ watchdog | 応答時間/エラー率/例外/起動失敗を継続収集 |
| A | - | 自動プロセス |
| C | 白瀬カイ（CTO）| 計測基盤実装・異常検知ロジック |
| C | 三枝ミオ（COO）| モジュール別メトリクス設計 |
| I | 全社員 | dashboard経由で参照可能 |

**検知対象モジュール（オーナー別）**:
- 実行エンジン: `dispatcher / employee_runner / multi_client` → @白瀬カイ
- 観察・監視: `architect_observer / watchdog / task_health` → @神楽アオイ
- コンテキスト: `context_assembler / state_digest / idea_capture` → @白瀬カイ + @三枝ミオ
- **自律ループ: `employee_autonomy / heartbeat / daily_loop` → @朝倉ノア（PMオーナー）**
- 設定: `dynamic_config.yaml / .env` → @白瀬カイ
- メトリクス: `usage_metrics / health_metrics` → @三枝ミオ

### Phase 2: 改修議論（ボトルネック/バグ検知後）

| 役割 | 担当 | 内容 |
|------|------|------|
| D | 白瀬カイ（CTO）| 技術的改修案の主導 |
| A | **朝倉ノア（PM）** | 優先度判断・スコープ縛り・完了条件定義 |
| A | 有馬レイジ（CEO）| 致命変更（本番影響大）のみ最終承認 |
| C | 全9社員 | 改修案提出（担当モジュール観点） |
| C | Architect | 致命変更時のみ参加 |
| I | 全社員 | 改修内容と完了条件を共有 |

**PM役割の具体**:
- 「この改修で誰が嬉しいか」「完了条件は何か」「v0.1はどれか」を議論前に確定
- 致命変更と軽微改修の分類（Architectレビュー要否の振り分け）
- 自律ループ（自分担当）の改修は利害関係者として意見述べ、最終判断はCTO

### Phase 3: 実装（git branchで本番分離）

| 役割 | 担当 | 内容 |
|------|------|------|
| D | 白瀬カイ（CTO）| Codex/Claude Code でコード生成 |
| A | **朝倉ノア（PM）** | 完了条件確認（実装done = 議論で定義した条件を満たすか） |
| C | - | カイ単独実装を基本とする |
| I | 三枝ミオ（COO）| テストフェーズへの引き渡しを把握 |

**ルール**:
- 本番 dispatcher を止めない（git branch + 別 venv 必須）
- 自律ループモジュール変更時はノアへ事前通知

### Phase 4: レビュー

| 役割 | 担当 | 内容 |
|------|------|------|
| D | Architect（設計者）| 致命変更のコードレビュー |
| A | Architect | 致命変更承認 |
| A | **神楽アオイ（監査）** | 軽微改修の監査承認 |
| C | 白瀬カイ | レビュー対応 |
| I | 有馬レイジ（CEO）| 致命変更のみ報告 |

**致命変更の定義**（このいずれかに該当）:
- dispatcher / multi_client のコアロジック変更
- 全社員の応答挙動に影響する変更
- bot/ 外部API接続方式の変更

### Phase 5: テスト

| 役割 | 担当 | 内容 |
|------|------|------|
| D | 白瀬カイ（CTO）| git branch 環境での動作確認 |
| A | **朝倉ノア（PM）** | デプロイ GO / NO GO 判断 |
| C | - | |
| I | 三枝ミオ（COO）| テスト結果を把握 |

**テスト失敗時**: 2回失敗 → 改修案廃棄 + 議論フェーズに差し戻し

### Phase 6: デプロイ

| 役割 | 担当 | 内容 |
|------|------|------|
| D | 白瀬カイ（CTO）| watchdog経由 safe restart 実行 |
| A | **朝倉ノア（PM）** | デプロイ最終GO（Phase 5テスト済みを確認） |
| C | watchdog | 不具合時の自動ロールバック |
| I | 全社員 | デプロイ開始・完了を経営会議へ |

**ロールバック発動時**: watchdog自動実行 → CEO即報告 → ノアが原因調査を議論フェーズに差し戻し

### Phase 7: 検証・学習

| 役割 | 担当 | 内容 |
|------|------|------|
| D | 三枝ミオ（COO）| デプロイ後 1h/24h でメトリクス比較 |
| A | - | 事実確認、承認不要 |
| C | 神楽アオイ（監査）| 異常・悪化の検知 |
| I | 全社員、Architect | 結果を共有 |
| 記録 | 白瀬カイ | `code_improvement_log.md` に効果と教訓を永続記録 |

**悪化判定時**: 三枝ミオが悪化を報告 → ノアが「ロールバックか継続様子見か」をCEOに諮る

## エスカレーション条件

| 条件 | 対応 |
|------|------|
| 本番dispatcher停止が必要な変更 | Architect必須レビュー後にCEO最終承認 |
| 自動ロールバック発動 | watchdog自動実行 + CEO即報告 |
| テスト2回失敗 | 改修案廃棄 + Phase 2（議論）差し戻し |
| 改修後24hで指標悪化 | ロールバック提案 → CEO判断 |
| いくとの単発作業が必要 | いくとへエスカレート（継続作業禁止ルール適用） |

## 事業指標DACIとの違い

前回作成 `2026-05-21_self_improvement_loop_daci.md` は**事業指標改善**（何を出すか）を対象とした。
本ドキュメントは**コードベース改修**（仕組みをどう動かすか）が対象。

| 観点 | 事業指標DACI | コード改修DACI |
|------|------------|-------------|
| Driver（主役） | ノア（PM）| カイ（CTO）|
| 承認者 | レイジ（CEO）| ノア（PM）+ Architect |
| 観察者 | ミオ（COO）| アオイ（監査）+ watchdog |
| 安全装置 | エスカレーション条件 | ロールバック + 2回テスト失敗廃棄 |
