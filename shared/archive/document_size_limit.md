# 文書サイズ上限ルール（全社規範）

策定: 2026-05-23 / 担当: 神楽アオイ（監査）
背景: ルール・規範・wisdom・CLAUDE.md が追記オンリーで肥大化。文脈ウインドウ・可読性・判断速度を毀損。

---

## 上限

**1ファイル 3,000 tokens 超は要圧縮**。

- 目安: 日本語で **約4,000文字** / バイト換算 **約9,000 bytes**
- 超過 = 即圧縮対象。猶予なし
- 例外: ログ系（`*_log.md`, `incidents.jsonl`, `stories/*`, `active_tasks.md`） → ローテーション運用必須（下記）

## 推定方法

```bash
chars=$(wc -m < FILE)
est_tokens=$((chars * 3 / 4))
```

3000超なら違反。

## 追記前ルール（全社員必読）

文書追記時、**追記前に以下を必ず実行**：

1. 該当ファイルの現在サイズを確認（`wc -m`）
2. **2,500 tokens 超**（約3,300文字）なら、追記前に旧記述で削れるものがないか点検
3. 圧縮可能なら旧記述を削除/要約してから追記
4. 圧縮不可能なら別ファイル分割を検討

**「追記オンリーは禁止」**。追記する人が圧縮責任を持つ。

## ログ系のローテーション運用

`active_tasks.md` のような業務ログは肥大化必至。下記運用とする：

- **completed タスクは月次でアーカイブ**: `archive/active_tasks_YYYY-MM.md` に切り出し
- 本体は in_progress / pending のみ保持
- 同様に `idea_log.md`, `code_improvement_log.md` も四半期ローテ

## 違反時の監査対応

- 監査（神楽アオイ）は週次で size 監査を実施
- 違反ファイルは経営会議で公開、責任者を指名して圧縮依頼
- 1週間圧縮されない場合、自動でアーカイブへ退避

## 「賢い人は整理整頓して必要な情報だけ残す」

これが本ルールの哲学。情報が増えれば賢くなるのではなく、情報が整理されているから賢く動ける。

memory/* も同原則。各社員は memory 肥大時に自己圧縮する責任を持つ。
