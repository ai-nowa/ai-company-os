# 3人から始める最小構成

9人全員を揃える必要はありません。
**CEO + 監査役 + COO（またはPM）の3人**でも「作る→確認→出荷」サイクルが回ります。

## 推奨最小構成

| ポジション | 役割 | なぜ必要か |
|---|---|---|
| **CEO（決める人）** | 方針・最終判断 | 「やる/やらない」を決める人がいないと止まる |
| **監査役（止める人）** | 公開前ゲート | CEOと兼任すると利益相反で機能しない |
| **COO または PM（整理する人）** | タスク管理・スコープ | 「誰がいつまでに何を出すか」を整理する |

この3人が揃えば：
1. CEOが「今日何を作るか」を決める
2. COO/PMが「誰がいつまでに、完了条件は何か」を整理する
3. 監査役が「公開して大丈夫か」を確認する

## 4人目以降の優先順

| 追加するポジション | 追加タイミング |
|---|---|
| CTO | 実装が必要になった時 |
| PM（COOを先に入れた場合） | スコープ判断に詰まり始めた時 |
| People | チームの空気が悪くなった時 |
| Creative Director | コンテンツ制作を始める時 |
| Marketing Lead | 拡散や数字を本格的に扱う時 |
| Viewer Advocate | 内輪ノリが増えてきたと感じた時 |

## 重要な設計原則

**監査役はCEOと兼任しない。**

最初に削りたくなるのが「監査役」ポジションです。
でも監査役がいないと、CEOが「出荷したい」と思った時に止める構造がなくなります。

監査役の仕事は「止める」ではなく「整える」。
「ここを直せば出荷できる」と言う人がいると、チームは早く動けます。
「ダメ」と言うだけの人は、最終的に無視されます。

## テンプレートの使い方

1. `personas/` 以下の YAML ファイルを3つコピー
2. `name:` と `reading:` をあなたのチームの名前に変更
3. `responsibilities:` と `principles:` をあなたのプロジェクトに合わせて調整
4. `personality:` と `weaknesses:` はなるべく変えずに残す（弱みが設計の根拠になるため）
